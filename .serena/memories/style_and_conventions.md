# Style And Conventions
- Use OpenSpec as the source of truth for planning and contract work.
- Keep changes narrow, milestone-oriented, and implementation-agnostic when working in proposals/specs/designs.
- Specs should use normative language (`MUST`) and testable observable scenarios instead of implementation details.
- Prefer a small stable public contract over broad MVP scope.
- Favor explicit writes, archive-over-delete semantics, and inspectable infrastructure.
- Keep capability names stable and avoid bundling storage or deployment choices into API-facing specs.
